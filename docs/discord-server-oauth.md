# Discord OAuth: отдельная авторизация каждого пользователя Nami

## Что реализовано

Один self-host сервер использует одно Discord-приложение, зарегистрированное администратором. Каждый пользователь Nami отдельно проходит OAuth и подключает собственный Discord-аккаунт. Ему не требуется создавать своё Discord-приложение или передавать токен аккаунта.

Связь: `Nami user_id → Discord user ID → индивидуальные OAuth access/refresh tokens`. На одном сервере один Discord-аккаунт может быть привязан только к одному пользователю Nami. Все устройства одной учётной записи видят одну привязку. Другая учётная запись имеет собственные токены и статус.

Основной поток: **WebUI → Профиль → Discord → Подключить Discord**. Пользователь проходит OAuth в Discord и возвращается в WebUI по ссылке. На телефоне нужно войти в **тот же аккаунт сервера Nami**; при воспроизведении приложение автоматически передаёт состояние серверу. Вводить Application ID или токен Discord на телефоне для этого не требуется. Браузер после привязки можно закрыть.

Альтернативный вход из Android: **Настройки → Плеер → Discord · учётная запись на сервере**. Статус обновляется при возврате из браузера; есть и ручная кнопка. Отключение действует только для текущего пользователя и останавливает его публикацию.

Серверный издатель реализован в `server/src/discord_presence.rs` и `server/discord-bridge/`. Он запускает официальный Social SDK с OAuth-токеном пользователя, ждёт состояния Ready и проверяет Discord user ID перед публикацией. На каждого активно слушающего пользователя запускается отдельный SDK-процесс. Прямой RPC через установленный на сервере Discord не используется.

**Текущий предел проверки:** Rust, WebUI и Android без локального SDK проверены. Нативный серверный мост не собран и реальная публикация не проверена: для этого нужен официальный пакет SDK и зарегистрированное Discord-приложение. Наличие OAuth-привязки само по себе не подтверждает публикацию. Без запускающегося SDK-моста API возвращает `presence_supported: false`; интерфейсы явно объясняют причину. Даже успешная проверка запуска моста подтверждает только доступность библиотеки; статус `published` появляется лишь после успешного ответа SDK.

## Настройка администратором

1. Создайте приложение в [Discord Developer Portal](https://discord.com/developers/applications) и включите Social SDK.
2. Используйте confidential client: `Client Secret` находится только на сервере, Public Client для этого потока не нужен.
3. В OAuth2 Redirects зарегистрируйте точный адрес, например:

   ```text
   https://music.example.com/api/discord/callback
   ```

4. Передайте серверу четыре переменные окружения:

   ```text
   NAMI_DISCORD_CLIENT_ID=<application ID>
   NAMI_DISCORD_CLIENT_SECRET=<client secret>
   NAMI_DISCORD_REDIRECT_URI=https://music.example.com/api/discord/callback
   NAMI_DISCORD_TOKEN_KEY=<64 hex-символа, 32 случайных байта>
   ```

   Ключ можно сгенерировать командой `openssl rand -hex 32`. Сохраните его в защищённой конфигурации сервера и резервной копии отдельно от БД. Не меняйте ключ при обычном обновлении: старые токены нельзя расшифровать другим ключом. Код не выводит ключ или client secret в Debug-представлении конфигурации.

5. Перезапустите сервер. `server/docker-compose.yml` уже передаёт эти переменные контейнеру. Все четыре могут быть пустыми — интеграция отключена. Частичная/некорректная конфигурация приводит к понятной ошибке запуска.

6. Установите SDK-мост по инструкции ниже и задайте `NAMI_DISCORD_BRIDGE`. Для работы сервера с телефона Android AAR не нужен: SDK находится на сервере.

OAuth redirect должен использовать HTTPS; HTTP разрешён только для localhost-разработки. Адрес должен открываться браузером пользователя телефона. Не используйте адрес из недоверенного заголовка Host и не записывайте query-параметры callback в access-логи reverse proxy.

Запрашиваются scopes `identify openid sdk.social_layer_presence`. Сервер получает Discord user ID через `/users/@me`; ID пользователя не берётся из параметров приложения или callback.

## API

Все `/api/me/discord*` требуют `Authorization: Bearer <Nami token>` и реальный `user_id`. Подходит сессия пользователя или его привязанное устройство. Анонимное устройство, гость Джема без учётной записи, query-токен и чужой `user_id` не дают доступа. У владельца сервера через эти маршруты нет обхода для чтения чужих токенов.

| Метод | Маршрут | Результат |
| --- | --- | --- |
| GET | `/api/me/discord` | Статус только текущего пользователя; username/Discord ID/expiry, без токенов |
| POST | `/api/me/discord/authorize` | OAuth URL с одноразовым state и PKCE S256 |
| GET | `/api/discord/callback` | Публичный callback; проверяет state и первоначальную сессию |
| POST | `/api/me/discord/refresh` | При необходимости обновляет только токены текущего пользователя |
| DELETE | `/api/me/discord` | Удаляет собственную привязку и незавершённый OAuth-поток |
| POST | `/api/me/discord/playback` | Принимает текущее воспроизведение только для владельца Nami credential |

Издатель автоматически обновляет OAuth-токены перед запуском и в фоне во время прослушивания. Сетевое обновление не блокирует обработку остановки плеера или SDK callbacks. Access token остаётся на сервере и передаётся дочернему процессу через stdin, не через аргументы командной строки, логи или WebUI.

Пример payload плеера (клиент не задаёт целевой user ID):

```json
{"playing":true,"title":"Название трека","description":"Исполнитель · Джем","position_ms":15000,"duration_ms":180000,"takeover":true}
```

`{"playing":false}` останавливает публикацию с отправившего устройства. Флаг `takeover` используется только при явном начале воспроизведения или смене трека: периодический сигнал от другого устройства не перехватывает активность. `accepted:false` означает, что сейчас публикует другое устройство этого пользователя.

## Сборка SDK-моста

Скачайте C++ Social SDK для ОС и архитектуры **сервера** в [Developer Portal](https://discord.com/developers/applications), раздел Social SDK → Downloads. Используйте заголовки и библиотеку из одного официального выпуска с `GetCurrentUserV2`. Код ориентирован на актуальный API Social SDK; совместимость конкретного пакета необходимо проверить сборкой и входом в тестовый аккаунт.

В примере ниже замените пути на реальные. `DISCORD_SDK_LIBRARY` — полное имя `.so`/`.dylib` либо импортной `.lib` для Windows:

```text
cmake -S server/discord-bridge -B server/discord-bridge/build -DDISCORD_SDK_INCLUDE_DIR=/opt/discord-sdk/include -DDISCORD_SDK_LIBRARY=/opt/discord-sdk/lib/release/libdiscord_partner_sdk.so
cmake --build server/discord-bridge/build --config Release
```

На Windows используйте инструменты сборки и SDK-библиотеки совместимой архитектуры; DLL из того же пакета должна находиться рядом с exe или в пути поиска DLL. На Linux для перенесённого бинарника положите библиотеку SDK рядом с ним и установите зависимости, перечисленные для SDK. Для сборки из каталога CMake использует путь к указанной библиотеке.

Перед запуском Nami проверьте:

```text
/absolute/path/nami-discord-bridge --check
```

Ожидаемый stdout: `nami-discord-bridge-v1`. Задайте `NAMI_DISCORD_BRIDGE=/absolute/path/nami-discord-bridge` (на Windows абсолютный путь к exe) и перезапустите сервер. SDK-мост проверяется при запуске Nami; после его установки нужен перезапуск.

В Docker переменная указывает на путь **внутри контейнера**. Обычный образ не включает проприетарный SDK: добавьте мост и подходящие SDK-библиотеки в собственный образ либо read-only volume. Например, в дополнительном Compose-файле:

```yaml
services:
  nami:
    environment:
      NAMI_DISCORD_BRIDGE: /opt/nami-discord/nami-discord-bridge
    volumes:
      - /srv/nami-discord:/opt/nami-discord:ro
```

Библиотека и мост должны быть собраны для ОС, libc и архитектуры контейнера. Один SDK-процесс нужен на каждого одновременно слушающего пользователя; измерьте расход памяти перед массовым использованием на малом сервере.

## Поведение при прослушивании

- Телефон проверяет привязку при воспроизведении, затем каждые 30 секунд. Передаёт изменения трека, перемотку и режим; при непрерывном воспроизведении подтверждает состояние раз в 15 секунд.
- Сервер формирует временные отметки по своим часам и позиции плеера. Передаются только метаданные, без аудио, кодов комнат и приватных URL обложек.
- Публикации объединяются с интервалом не менее пяти секунд. При паузе SDK-процесс очищает активность и отключается; обычная задержка ограничена сетевым запросом и секундным опросом издателя.
- При потере телефона состояние истекает через 60 секунд после последнего принятого сообщения. Сбой самого сервера закрывает stdin моста; зависший сервер дополнительно отслеживается 45-секундным watchdog моста. Фактическое исчезновение профиля зависит и от доставки/обработки Discord.
- Отзыв или перепривязка Nami-устройства, удаление пользователя и отключение Discord прекращают публикацию старого источника. При смене Discord ID старый SDK-процесс завершается перед новым.
- Состояние плеера хранится в памяти и не восстанавливается после перезапуска без нового сообщения телефона.
- Показываются режимы «Джем», «Слушать вместе», «Раздача» из реального состояния плеера. Это подписи активности; создание новых Discord-приглашений и воспроизведение через кнопки Spotify сюда не входят.
- При выбранной доступной серверной публикации прямой Android RPC приостанавливается, чтобы две интеграции не спорили за активность. Переключатель отображения режима работает для обоих способов.

## Хранение и конкуренция

- `discord_connections.user_id` — первичный ключ и FK на users с `ON DELETE CASCADE`.
- Access/refresh tokens шифруются AES-256-GCM со случайным nonce. Аутентифицированные данные шифрования содержат `user_id` и Discord Application ID: перенос зашифрованной строки другому пользователю не даёт рабочего токена.
- Временный OAuth state хранится только в виде хеша, связан с пользователем и хешем исходного Nami credential, живёт 10 минут и используется один раз.
- Повторный старт отменяет предыдущую попытку того же пользователя.
- Callback повторно проверяет исходный credential: отозванное или перепривязанное устройство не завершает старую привязку.
- Отключение во время обмена кода удаляет pending-запись. Поздний callback не восстанавливает удалённую привязку.
- Refresh резервирует короткую аренду на строке пользователя; обновление использует сравнение предыдущего шифротекста. Поздний результат не заменяет новую привязку и не создаёт заново удалённую.
- Ответы OAuth помечены `Cache-Control: no-store`; callback не содержит внешних ресурсов, токены в браузер не передаются.
- При отключении локальная запись удаляется сразу. Сервер пытается отозвать grant в Discord; если Discord недоступен или изменился ключ, ответ содержит `revoked_remotely: false`, а интерфейс предлагает отозвать разрешение в Discord вручную.

Новые таблицы создаются идемпотентно при открытии существующей БД. Существующие учётные записи и привязанные устройства сохраняются.

## Проверка

```powershell
cd server
cargo test discord
```

Тесты проверяют HTTP-изоляцию двух пользователей, запрет query-токенов и анонимных устройств, одноразовый/просроченный state, отзыв credential, гонку отключения с callback, шифрование с привязкой к пользователю и приложению, удаление аккаунта и неполные OAuth grants. Дополнительно проверяются отправка состояния телефона, смена владельца устройства, пауза, истечение heartbeat и отбрасывание запоздалого подтверждения предыдущего трека. `node --test web/tests/discord.test.cjs` проверяет WebUI OAuth, смену аккаунта во время запроса, разрешённый redirect и честный статус без SDK.

Проверка настоящего OAuth требует настроенного Discord-приложения и callback-домена. Без них можно проверить код и изоляцию, но нельзя заявлять об успешном входе через Discord.

Результаты проверки 2026-09-15: сервер — 142 passed, 1 ignored; WebUI — 5 passed; Android `:app:hiltJavaCompileDebug :data:testDebugUnitTest :domain:test` — успешно, сборка без локального Discord SDK.

При проверке с настоящим SDK откройте WebUI под двумя разными Nami-пользователями, авторизуйте два разных Discord-аккаунта, запустите разные треки на двух телефонах и проверьте оба профиля с третьего аккаунта. Затем проверьте паузу, потерю сети более 60 секунд, перемотку, смену режима, отзыв привязки и обновление истёкшего токена. До этого теста нельзя считать публикацию через Discord подтверждённой.

Официальные источники: [OAuth2](https://docs.discord.com/developers/topics/oauth2), [серверный обмен, обновление и отзыв Social SDK токенов](https://docs.discord.com/developers/discord-social-sdk/development-guides/account-linking-with-discord).
