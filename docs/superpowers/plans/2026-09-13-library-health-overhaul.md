# Улучшение «Здоровья библиотеки»

> **Для агентов:** реализовывать по задачам, отмечая шаги галочками (`- [ ]`). Каждая задача оставляет рабочее приложение.

**Цель.** Экран «Здоровье библиотеки» сейчас находит шесть видов проблем и умеет чинить пять. Он медленный на большой библиотеке, пересчитывает весь отчёт после каждого исправления, не умеет чинить пачкой, не помнит отклонённые ложные срабатывания и полностью игнорирует отчёт сервера, хотя клиент для него уже написан.

**Что есть сейчас** (не переписывать, а достраивать):
- `domain/src/main/kotlin/dev/nami/domain/LibraryHealth.kt` — модель `LibraryHealthReport`, шесть категорий.
- `data/src/main/kotlin/dev/nami/data/LibraryRepositoryImpl.kt:88` — `libraryHealthReport()`, там же `duplicateGroups()` с union-find по двум признакам: метаданные через `DedupKey` и отпечаток звука `AudioFingerprint`.
- `feature/library/src/main/kotlin/dev/nami/feature/library/LibraryHealthViewModel.kt` — пять действий-исправлений, порционное сканирование отпечатков по кнопке.
- `feature/library/src/main/kotlin/dev/nami/feature/library/LibraryHealthScreen.kt` — categories в `LazyColumn`.
- `server/src/library.rs` — серверный отчёт `Health` с полями `tracks`, `broken`, `missing`, `without_artist`, `without_album`, `without_year`, `duplicate_groups`.

**Стек.** Kotlin, Compose, Room, Hilt. Новых зависимостей не добавлять.

## Общие ограничения

- Цвета и отступы — только токены `NamiColors`, без новых hex-литералов.
- Каждое новое правило проверки обязано иметь либо исправление, либо честное объяснение, почему исправления нет. Не добавлять категорию, которая только пугает числом.
- Никаких «догадливых» проверок: спектрального анализа для поиска поддельного hi-res в проекте нет, и приблизительную версию делать не надо — так уже решено в комментарии к `LibraryHealth.kt`.
- Не ломать CUE: несколько строк с одним `path` и разными `cueStartMs` — не дубли и не битые файлы.

### Задача 1. Убрать квадратичную стоимость отчёта

Сейчас на каждый трек библиотеки делается отдельная работа:
- `lyricsRepository.lyricsForPath(it.path).first()` — по одному подписыванию на Flow на трек;
- `File(it.path).exists()` — по одному системному вызову на трек.

На нескольких тысячах треков это заметная пауза при каждом открытии экрана и после **каждого** исправления, потому что `refresh()` пересчитывает отчёт целиком.

**Файлы:** `data/.../LibraryRepositoryImpl.kt`, `domain/.../LyricsRepository.kt`, `core/database/.../dao/TrackDao.kt`.

- [ ] Добавить в `LyricsRepository` пакетный метод — вернуть множество путей, для которых текст есть, одним запросом, и использовать его вместо цикла.
- [ ] Заменить поштучный `File.exists()` на обход каталогов: собрать множество существующих файлов по родительским папкам (`listFiles()` на каждую уникальную папку), затем сверять по множеству. Папок на порядки меньше, чем треков.
- [ ] Проверить на библиотеке из нескольких тысяч строк, что отчёт строится за разумное время. Замер до и после — в отчёт о выполнении.

### Задача 2. Не пересчитывать весь отчёт после каждого исправления

`LibraryHealthViewModel` вызывает `refresh()` после каждого действия, включая исправление одного альбома или одного артиста.

**Файлы:** `feature/library/.../LibraryHealthViewModel.kt`.

- [ ] Локально обновлять только затронутую категорию: удалили трек — убрать его из списков, проставили год — убрать альбом из `albumsWithoutYear`, слили имена — убрать группу.
- [ ] Полный `refresh()` оставить кнопкой и первым открытием экрана.
- [ ] Юнит-тест: после `setAlbumYear` список альбомов без года укоротился, а остальные категории не перестраивались (подсчитать число обращений к репозиторию в фейке).

### Задача 3. Массовые исправления

Сейчас каждое исправление — отдельное нажатие. На библиотеке с сотней проблем это неприменимо.

**Файлы:** `feature/library/.../LibraryHealthViewModel.kt`, `LibraryHealthScreen.kt`.

- [ ] «Слить все имена артистов» — одним действием по всем группам.
- [ ] «Удалить все пропавшие файлы» — с подтверждением и указанием числа.
- [ ] «Скачать недостающие тексты» — порциями, с прогрессом и возможностью остановить: это сетевые запросы к LRCLIB, по одному на трек.
- [ ] «Разрешить все группы дублей» — оставляя лучший экземпляр, см. задачу 4. Только с подтверждением и предпросмотром того, что будет удалено.
- [ ] Каждое массовое действие должно быть прерываемым и не блокировать экран.

### Задача 4. Осмысленный выбор экземпляра в группе дублей

`resolveDuplicateGroup(keepId, group)` требует, чтобы пользователь сам выбрал, что оставить, а экран не даёт никаких оснований для выбора — только название.

**Файлы:** `domain/.../LibraryHealth.kt`, `data/.../LibraryRepositoryImpl.kt`, `LibraryHealthScreen.kt`.

- [ ] Расширить `HealthTrackRef` данными, по которым видно качество: формат, битрейт (уже считается как `sizeBytes * 8 / durationMs`), частота дискретизации, разрядность, размер файла.
- [ ] Показывать эти данные в строке группы, чтобы выбор был осознанным.
- [ ] Предлагать лучший по правилу: lossless важнее lossy, затем выше частота и разрядность, затем больше битрейт, при равенстве — тот, что добавлен раньше. Предложение должно быть видимым и переопределяемым, а не молча применяться.

### Задача 5. Отклонённые срабатывания не должны возвращаться

Отчёт не помнит решений пользователя. Если два трека — не дубли, они будут показываться дублями вечно.

**Файлы:** новая таблица в `core/database`, миграция схемы (текущая версия 31, миграции в `core/database/.../migration/Migrations.kt`, регистрация в `di/DatabaseModule.kt`).

- [ ] Таблица игнорирований: вид проверки плюс ключ (для дублей — пара идентификаторов треков в устойчивом порядке).
- [ ] Действие «это не дубли» и «пропустить» в остальных категориях.
- [ ] Раздел «скрытые замечания» со счётчиком и возможностью вернуть — иначе пользователь потеряет то, что скрыл по ошибке.
- [ ] Не забыть удалять записи об игнорировании, когда трек удалён, иначе таблица будет расти вечно.

### Задача 6. Новые проверки

Что уже умеет находить сервер, но не умеет приложение (`server/src/library.rs`): треки без артиста, без альбома, битые файлы. Плюс то, чего нет ни там, ни там.

**Файлы:** `domain/.../LibraryHealth.kt`, `data/.../LibraryRepositoryImpl.kt`, `LibraryHealthScreen.kt`.

- [ ] Треки без артиста и без альбома. Исправление — открыть редактор метаданных, он уже есть.
- [ ] Треки с нулевой или отсутствующей длительностью: обычно признак недокачанного или битого файла.
- [ ] Файлы-сироты в `filesDir/music`, на которые не ссылается ни одна строка `tracks`. Занимают место молча. Исправление — удалить, с указанием освобождаемого объёма.
- [ ] Осиротевшие `.lrc` рядом с несуществующими треками.
- [ ] Плейлисты, ссылающиеся на удалённые треки.

- [ ] Обложки: строка `albums.artworkPath` указывает на несуществующий файл.

Каждый пункт — отдельный шаг с исправлением и тестом. Если для проверки нет разумного исправления, категория всё равно полезна, но это надо явно указать в интерфейсе.

### Задача 7. Отчёт сервера в приложении

**Файлы:** `domain/.../ServerLibraryRepository.kt`, `data/.../ServerLibraryRepositoryImpl.kt`, `LibraryHealthScreen.kt`.

- [ ] Довести отчёт сервера до экрана отдельным разделом «На сервере», когда сервер подключён.
- [ ] Учесть форму ответа: каждый список — объект `{count, items}`, а `items` обрезан до `SAMPLE_LIMIT`. Показывать полное число и выборку, не выдавая выборку за весь список.
- [ ] Исправления серверных проблем — только те, для которых есть эндпоинт. Чего нет, то показывать без кнопки, а не делать вид.

## Порядок

Задачи 1 и 2 — первыми: они делают экран пригодным для работы, и на них опирается всё остальное. Дальше 3 и 4 (массовые исправления и выбор в группе дублей) дают наибольшую пользу на существующих данных. 5 нужна до того, как появятся новые проверки из задачи 6, иначе новые ложные срабатывания будет нечем скрыть. 7, 8 и 9 независимы и делаются в любом порядке.

## Осознанно не входит

- Поиск поддельного hi-res: нужен спектральный анализ, которого в проекте нет. Приблизительная версия хуже отсутствия — так уже решено в `LibraryHealth.kt`.
- Автоматическая загрузка обложек из сети: источника обложек в проекте нет, извлекается только встроенная при импорте.
- Автоматическое удаление чего-либо без подтверждения. Отчёт о здоровье — советчик, а не уборщик.
